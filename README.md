# Просмотр 3D-моделей

Просмотрщик STL, 3MF и нарезанного G-code. Его можно вставить на сайт одной
строкой, а можно открыть в правой боковой панели DeepSeek Harness — это одна и
та же панель, и плагин здесь только один из хостов.

```html
<script src="embed/dist/model3d-viewer.js"></script>
<model3d-viewer src="./деталь.3mf" language="ru"></model3d-viewer>
```

Без React, без сборщика, без зависимостей: движок — это WebGL и разбор файлов,
панель — обычный DOM.

Работает с любыми файлами этих форматов.

## Что умеет

- **STL** — бинарный и ASCII.
- **3MF** — включая проекты OrcaSlicer и AnycubicSlicer: объекты из отдельных
  `.model`-частей, назначения филаментов, раскраска кистью (`paint_color`).
- **G-code** — обычный `.gcode` и нарезанный 3MF со встроенным
  `Metadata/plate_1.gcode`.
- **Два вида** для нарезанных файлов: «Модель» (исходная геометрия) и «Нарезка»
  (штрихи, как их положил слайсер). Если файл содержит нарезку, она открывается
  по умолчанию.
- **Ползунок слоёв** с двумя границами и отдельной кнопкой «показать один слой».
  Сделан по образцу OrcaSlicer: утопленный желоб, видимый диапазон залит
  фирменной бирюзой, ручки — кружки с крестиком.
- **Стол принтера** — прозрачная сетка по контуру из файла. Цвет сетки
  выводится из фона: нейтральный по тону, светлый на тёмном и тёмный на светлом.
  Толщина линий задана в пикселях, поэтому они остаются волосяными на любом
  масштабе.
- **Проигрывание печати** по кнопке: первый слой ложится штрих за штрихом, все
  следующие — послойно, в том порядке, в каком их писал слайсер.
- **Навигационный куб** — 26 областей (6 граней, 12 рёбер, 8 углов): клик
  разворачивает камеру, перетаскивание вращает.
- **Материал**: матовость, металличность, прозрачность — отдельно для каждого
  филамента, плюс общий уровень освещения. Всё это в том же окне цвета, над
  печатью, а не отдельной полосой.
- **Палитра** правится своим окном цвета — всплывающим под свотчем, без
  затемнения: поле насыщенности и яркости, полоса тона, поля HEX/RGB/HSV,
  палитра файла для копирования и пипетка. Цвет показывается на печати сразу,
  ещё до нажатия «Ок». Там же прозрачность нити: полоса с её цветом, гаснущим к
  прозрачному краю, и процент, который можно ввести руками.
- **Встраивается как элемент** `<model3d-viewer src height language>`: хост задаёт
  высоту атрибутом и перекрашивает панель своими CSS-переменными.
- **Сохранение в PNG** — 2048 px по ширине, файл называется по имени модели.
- **Два режима освещения**: студийный материал и простое затенение.
- **Настройки запоминаются для каждого файла**: свет, стол, фон, камера (угол,
  зум и смещение), материал и цвета нитей, диапазон слоёв. Кнопка сброса их стирает.
- **Трассировка лучей по кнопке**: мягкие падающие тени, контактное затемнение
  и отражения, которых растеризатор не умеет. Кадр набирается прогрессивно и
  чистится фильтром, а не только числом сэмплов.
- **Экспорт трассированного кадра** отдельным PNG: свой прогон, 1024 px, 160
  сэмплов, тот же фильтр.

## Управление

| Действие | Жест |
|---|---|
| Вращение | левая кнопка + перетаскивание |
| Сдвиг сцены | правая кнопка, средняя кнопка или Shift + левая |
| Масштаб | колесо |
| Пресет вида | клик по грани, ребру или углу куба |
| Вращение кубом | перетаскивание по кубу |

## Два способа использовать

| | Куда | Как |
|---|---|---|
| **Библиотека** | любой сайт | `embed/dist/model3d-viewer.js` + тег или `mount()` |
| **Плагин** | панель DSH | `client.js`, собранный из той же библиотеки |

Подробно про встраивание — [embed/README.md](embed/README.md). Ниже — про
плагин.

## Установка плагина

Плагин подключается к профилю `web` через `link:`-зависимость, поэтому правки
видны сразу после перезагрузки страницы, без переустановки.

```bash
git clone https://github.com/gromilov/model3d-viewer.git
cd model3d-viewer
node embed/build.mjs && node build.mjs
```

```
~/.dsh/profiles/web/cordis.patch.yml   ← тут строка model3d-viewer
```

`cordis.patch.yml` внутри плагина вставляет свою строку в дерево плагинов:

```yaml
- insert:
    - id: model3d-viewer
      name: 'model3d-viewer'
```

Половина для Host пустая (`index.js` содержит `export function apply() {}`) —
вся работа идёт на клиенте.

## Сборка

Две сборки из одних исходников.

```bash
node embed/build.mjs    # библиотека -> embed/dist/model3d-viewer.{mjs,js}
node build.mjs          # плагин    -> client.js
node verify/library.mjs # проверка в настоящем браузере
```

Обе — **генерируемые файлы**, руками не правятся. После сборки плагина
перезагрузить страницу (`Cmd+R`); переустановка не нужна.

### Почему один файл

Загрузчик DSH разрешает только платформенные пакеты (`react` и подобные),
поэтому `build.mjs` вырезает `export`/`import` и складывает модули в общую
область видимости. Порядок — это граф зависимостей:

```
paint → parsers → gcode → viewer → cube → dom → styles → i18n → loader → panel
```

`locale/*.json` встраивается так же — бандл остаётся одним скриптом без
дополнительных запросов. Та же последовательность используется в
`embed/build.mjs`, где она ещё и объявлена массивом `MODULES`.

**Осторожно с именами.** Всё лежит в одной области видимости, поэтому две
функции с одинаковым именем в разных модулях — это не ошибка сборки, а тихая
подмена: побеждает последняя. Однажды `cube.js` переопределил `compileShader`
из `viewer.js`, и ошибки шейдера модели репортились как ошибки куба. Функции
куба поэтому названы `cubeCompileShader`, `cubeLookAt`, `cubePerspective`.

## Устройство

Движок и панель живут в `embed/src/` и ничего не знают о DSH.

| Файл | Что делает |
|---|---|
| `embed/src/parsers.js` | STL, 3MF (ZIP + inflate), извлечение G-code из 3MF |
| `embed/src/paint.js` | палитра, `paint_color`, конверсия sRGB → линейное |
| `embed/src/gcode.js` | разбор G-code в инстансы штрихов |
| `embed/src/viewer.js` | WebGL: две программы (треугольники и штрихи) плюс стол |
| `embed/src/cube.js` | навигационный куб на своём canvas и контексте |
| `embed/src/panel.js` | панель целиком, без фреймворка |
| `embed/src/persist.js` | настройки на каждый файл, проверка хранимого |
| `embed/src/picker.js` | окно цвета: HSV, HEX/RGB, предпросмотр, пипетка, материал нити |
| `embed/src/bvh.js` | BVH по треугольникам и капсулам |
| `embed/src/tracer.js` | трассировщик: тени, AO, два отскока, денайзер, экспорт кадра |
| `embed/src/element.js` | `mount()` и тег `<model3d-viewer>` |
| `src/ui.js` | **адаптер DSH**: находит файл вкладки, читает его, ставит панель |

Адаптер знает ровно три вещи: как разобрать адрес вкладки, как прочитать её
байты и куда положить `<div>`. Всё остальное — в библиотеке.

### Штрихи, а не треугольники

Нарезанная плита — это сотни тысяч коротких отрезков. Рисовать каждый
двенадцатью треугольниками (4 боковые грани и 2 крышки) значит для самой
большой модели этой папки 5 миллионов треугольников и 174 МБ только под
позиции вершин. Вместо этого один квад на штрих с инстансингом: общее кольцо
вершин плюс по 12 чисел на штрих. Это даёт 3.6–19.3 МБ на файлах из этой
папки.

Нормаль в шейдере строится по сечению штриха, а не берётся из геометрии —
поэтому штрих затеняется как округлённое тело, хотя рисуется двумя
треугольниками.

### Сечение штриха — прямоугольник

OrcaSlicer использует ромб. Ромб покрывает ровно половину своего
прямоугольника, поэтому соседние штрихи соприкасаются по одной линии, а над и
под ней остаются треугольные щели. Сквозь них видны нижние слои с
противоположным углом заполнения — плита выглядит решёткой пересекающихся
фигур вместо сплошной поверхности.

Прямоугольник укладывается без щелей. Скругление профиля всё равно даёт
шейдер, так что ромб не был нужен.

### Цвет — в униформе, а не в буфере

Инстанс штриха хранит **номер слота палитры**, а не сам цвет. Смена цвета
филамента — это загрузка одной униформы вместо пересборки буфера на 78 тысяч
штрихов.

### Сколько стоит кадр

Полная плита — 153 000 штрихов, это 612 000 вершин за кадр. Всё, что ниже,
измерено на встроенной графике Intel Iris Plus, а не на дискретной.

| Что | Было | Стало |
|---|---|---|
| Один слой | 15,1 мс | **0,8 мс** |
| Половина слоёв с затемнением | 17,0 мс | **9,9 мс** |
| Вся плита | 19,4 мс | 19,4 мс |
| 60 движений мыши | 60 отрисовок | **не более 5** |

Две причины, обе неочевидные.

**Вершинный шейдер вызывался для всей плиты.** Скрытые слои отбрасывались уже
в шейдере, то есть после того, как для них выполнилась вся работа. Один слой
стоил столько же, сколько шестьдесят пять. Слайсер пишет послойно, поэтому
штрихи одного слоя лежат в буфере подряд — и диапазон теперь рисуется сдвигом
по атрибутам и укороченным счётчиком инстансов.

**Каждое движение мыши рисовало кадр.** Тачпад присылает несколько событий на
кадр, а `draw()` вызывался синхронно из обработчика: очередь росла быстрее, чем
успевала отрисоваться, и жест отставал от пальца. Теперь состояние обновляется
на каждое событие, а живопись — раз в кадр.

### sRGB и линейное пространство

Цвета в файлах заданы в sRGB, а шейдер считает свет в линейном пространстве.
Без конверсии на входе ошибка максимальна там, где глаз её лучше всего видит:
`#0d0a0a` приходил как 0.05 линейных вместо 0.004 — в двенадцать раз ярче,
поэтому чёрная деталь рисовалась серой, а разница в младших битах (13, 10, 10)
усиливалась в заметный красный оттенок.

### Освещение

Студийный материал: GGX для блика, Smith-Schlick для самозатенения,
Schlick-френель, wrapped diffuse (пластик рассеивает под поверхностью) и
ACES-тонмаппинг. Металличность меняет сразу две вещи, которые физически
различаются: у диэлектрика есть диффуз и белый блик 4%, у металла диффуза нет,
а отражение окрашено в цвет самого металла.

Цвет филамента применяется один раз как альбедо, а свет **добавляется** к нему,
а не умножает его. Иначе чёрный остаётся чёрным при любом освещении.

### Трассировка

Растеризатор не умеет того, что показывает форму: мягкой падающей тени,
затемнения в щелях и отражения модели в себе. По кнопке тот же кадр считается
лучами и набирается прогрессивно — по сэмплу за кадр.

Ускоряющая структура — BVH в текстуре: сотни тысяч штрихов укладываются за
доли секунды и занимают единицы мегабайт. Штрих трассируется как капсула (аналитическое пересечение, дешевле
треугольников), модель — как треугольники. Направления на свет джиттерятся
внутри маленького конуса, поэтому накопление усредняет много жёстких теней в
одну мягкую.

Два отскока: отражение освещается своим светом и своей тенью, так что в нём
видна тень, которой при одном отскоке не было бы. Свет, отражённый дважды, не
собирается — это не многократный GI.

Шум чистит **совместный билатеральный фильтр**, три прохода по радиусу 1, 2, 4.
Направляется он нормалью и глубиной: сосед учитывается, только если это та же
поверхность на том же расстоянии. Выигрыш честный, около 2× — один сэмпл с
фильтром выглядит как два без него, а не «в разы».

Выгрузка трассированного PNG считается заново на своём offscreen-трассировщике
(`createStillRender`): живой нельзя переиспользовать, потому что ресайз целей
уничтожает накопленный буфер, и интерактивный вид начинал делить пустоту. Кадр
экспорта — 1024 px и 160 сэмплов; на 2048 два набора целей рендера не влезали в
память, и файл молча получался пустым.

Считать его одним циклом нельзя: шесть с половиной секунд вкладка не отвечает, и
строка прогресса физически не успевает отрисоваться. Нарезка на слайсы по четыре
сэмпла тоже не помогла — вызов WebGL только **ставит работу в очередь**, поэтому
сорок слайсов возвращались мгновенно, а вся стоимость падала на финальное
чтение одним стопором в 4.6 с. Теперь каждый слайс заканчивается
синхронизацией, и самый долгий стопор — 0.37 с в цикле и 0.63 с на финальные
денайзер и кодирование PNG. Числа замерены, а не прикинуты.

## Проверки

```bash
node verify/library.mjs
```

Двадцать одна проверка в **настоящем браузере**: headless Chrome рисует WebGL
через ANGLE Metal, страница докладывает результат в `document.title`, а скриншот
читается обратно собственным декодером PNG и проверяется по пикселям.

| Проверка | Что подтверждает |
|---|---|
| демо-страница | монтируется и рисует |
| настройки | переживают пересоздание панели, сброс их стирает |
| восстановленный вид | картинка та же, что оставили: фон, стол, камера, цвет |
| экспорт PNG | фон картинки того цвета, что выбран, а не зелёный |
| трассировка | набирается до 60+ сэмплов, поверхность темнеет от теней |
| пустая сцена | отказывается трассировать и говорит почему |
| трассированный PNG | файл не пустой: 1024 px и десятки тысяч освещённых точек |
| выгрузка не морозит вкладку | цикл уступает потоку: прогресс наблюдается растущим |
| бюджет сэмплов не превышается | ровно 96 при лимите 96, а не 109 |
| панель целиком | иконки на месте, подписи слайдеров не пустые, ни один орган управления не спрятан |
| переключение видов | цвета те же до и после похода в нарезку (было 52 оттенка → 4) |
| диапазон слоёв и жест | рисуется только видимый срез, а не вся плита |
| сетка стола | нейтральная по цвету и контрастная на любом фоне |
| ползунок слоёв | желоб, заливка на выбранном диапазоне, цвет и положение ручек |
| 28 вызовов API | каждый орган управления доходит до движка и обратно |
| стол и куб | рисуются вместе на одном кадре |
| чистый `.gcode` | открывается на виде нарезки, со слоями и столом |
| полный `.gcode` | сотни тысяч штрихов и десятки слоёв, открывается |
| 12 циклов создать/освободить | не течёт GPU-контекст |
| классический скрипт | тег и глобальный объект появляются |
| `client.js` для DSH | регистрирует вкладку и монтирует панель |

Скриншоты **побитово воспроизводимы** между запусками, поэтому пороги по
пикселям не «плавают».

### Что это изменило

Раньше проверки были только в `/tmp`, вне репозитория, и внешний вид не
проверялся вообще: правки света и цвета — математикой и растеризацией в Node,
не глазами, потому что скриншоты в GUI недоступны из-за разрешений macOS.

Первые же прогоны в браузере нашли два настоящих дефекта, которые до этого
жили в коде:

- **Куб не открывался.** `gl.compileShader` когда-то был переименован в
  `gl.cubeCompileShader` — вместе со *своим* помощником. Сломался бы при первом
  показе куба.
- **Чистый `.gcode` не открывался.** `parseGcode` возвращает саму отрисовку, а
  не `{ mesh }`; панель читала `.mesh` и падала на `undefined`.

Прогоны трассировки нашли ещё три, каждый из которых выглядел как «работает»:

- **Денайзер был почти пустышкой.** Пороги фильтра были подобраны под sRGB
  0..255, а он работает на линейных значениях до тонмаппинга. После пересчёта —
  26% меньше ошибки на одном сэмпле.
- **«Независимые» кадры были побитово одинаковыми.** Затравка бралась из счётчика
  сэмплов, который обнулялся при перезапуске, — две выборки по одному сэмплу
  совпадали, и шум не усреднялся.
- **Экспорт в 2048 px молча отдавал пустой PNG.** Шесть целей рендера плюс второй
  полный набор на экспорт — около 300 МБ, контекст отказывал. На 1024 всё
  помещается, и с фильтром это выглядит лучше несфильтрованного 2048.

**Осталось непроверенным:** реальные жесты мышью и тачпадом. Скриншот
показывает результат, но не то, что перетаскивание ощущается правильно.

## Ограничения

- **Прозрачность без сортировки по глубине.** При сильной прозрачности слои
  могут накладываться в неверном порядке. До ~0.4 незаметно.
- **Экспорт в PNG — не трассировка лучей.** Это тот же WebGL-кадр в высоком
  разрешении: сглаживание за счёт размера, отражения приблизительные. Для
  трассированного файла есть отдельная кнопка.
- **Модель не перекрашивается.** Правка палитры работает только для нарезки; у
  модели цвета запечены по треугольникам.
- **STL рисуется одним нейтральным цветом** — файл не несёт цвета вообще.
- **Куб рисуется только при включённом столе.**
- **Фон в PNG всегда непрозрачный**, даже если сцена прозрачная.
- **Жесты не покрыты проверками** — только результат отрисовки.
- **Трассировка считает 96 сэмплов** и на этом останавливается: потолок, а не
  признак сходимости. На большом файле это около восьми секунд.
- **Трассировка: два отскока, многократного GI нет.** Отражение освещается своим
  светом и своей тенью, но свет, отражённый дважды, не собирается.
- **Денайзер пространственный, не обученный.** Три совместных билатеральных
  прохода по нормали и глубине дают честные 2× по шуму (1 сэмпл с фильтром
  выглядит как 2 без него), а не «в разы».
- **Трассировка требует WebGL2** и float-таргетов.
- **Настройки живут в браузере.** Очистка данных сайта их стирает, и между
  машинами они не переносятся.
- **Файлы для проверок не в репозитории.** Настоящие 3MF и G-code подкладываются
  скриптом `verify/fixtures.mjs` из папки рядом с чекаутом; в репозитории лежат
  два маленьких STL, а проверки без фикстур честно пропускаются.
